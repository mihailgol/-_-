# DEVELOPMENT_RULES.md — Правила разработки и Дорожная карта проекта ExamHub

Данный документ содержит полные инструкции, стандарты разработки, архитектурные правила и поэтапный план (Roadmap) развития веб-платформы **ExamHub** (подготовка к ЕГЭ/ОГЭ).

---

## 1. Архитектура и ограничения проекта

### 1.1 Стек технологий
* **Frontend:** Чистые HTML5, CSS3, Vanilla JavaScript (ES6+ модули `<script type="module" src="js/app.js">`).
  * ❌ **Запрещено:** использовать фронтенд-фреймворки (React, Vue, Svelte) или сборщики (Webpack, Vite, Parcel).
  * ❌ **Запрещено:** хардкодить данные из `js/data.js` в клиентской логике — все данные приходят с сервера через API `/api/catalog/subjects`.
  * ✅ **Иконки:** Vendored библиотеку [lucide.min.js](file:///c:/Users/мишка/Desktop/сайтик_бахчасарай/js/lucide.min.js) (не модифицировать).
* **Backend:** Node.js (>=18, `"type": "module"`) + Express.
  * **База данных:** SQLite (`node:sqlite`, `DatabaseSync`, режим WAL).
  * **Авторизация:** HTTP-only сессионные куки `examhub_session`, хеширование `bcryptjs`.

### 1.2 Языковые и стилевые стандарты
* **Язык интерфейса:** Только русский.
* **Имена в коде:** Английский язык для переменных, функций, классов, CSS-селекторов и файлов.
* **Комментарии:** ❌ **Не добавлять комментарии в код** без явного запроса пользователя.

### 1.3 Глобальный контекст экзамена (ЕГЭ / ОГЭ)
* ⚠️ **Главная верхняя строка (Header):** Переключатель «Все / ЕГЭ / ОГЭ» в шапке сайта всегда является **ГЛАВНЫМ (Master)**. Его выбор определяет весь контекст работы платформы для конкретного пользователя.
* ❌ **Запрещено:** выводить одинаковый набор тестов, предметов, вариантов и теории для ОГЭ и ЕГЭ. Контент должен строго фильтроваться по выбранному типу экзамена.

## 2. Стандарты разработки и кодстайл

### 2.1 Фронтенд (js/modules/*)
1. **Модульность:** Каждый модуль отвечает за свою сферу (навигация, авторизация, плеер квизов, аналитика и т.д.).
2. **Работа с DOM:**
   * Все интерактивные элементы должны иметь уникальные `id` или понятные `data-view`/`data-action` атрибуты.
   * Обязательно очищать контейнеры (например, `container.innerHTML = ""`) перед повторным рендером для предотвращения дублирования элементов.
3. **История браузера и роутинг:**
   * Обычные экраны переключаются через `switchView(name)`.
   * Вложенные экраны (sub-views, например конспект или вариант теста) пушатся через `pushSubView(state, hash)` с **уникальным hash-URL** (например, `#subject-detail:math`, `#note-reader:bio:1`). Это критично для правильной работы кнопок браузера «Назад»/«Вперёд».

### 2.2 Форматирование и линтинг
* Поведение Prettier настроено в `.prettierrc.json` и `.prettierignore`.
* ⚠️ **Важно:** файлы `js/app.js` и `index.html` **исключены из Prettier** — не пытаться форматировать их автоматически на всю длину строк.

## 3. Обязательный регламент проверки (Quality Gate)

Перед завершением любой задачи ИИ-агент или разработчик **обязан** выполнить полную проверку проекта:

```bash
npm run check
```

Эта команда последовательно запускает:
1. `npm run lint` — проверка ESLint.
2. `npm run build` — валидация структуры и связей проекта ([validate-project.mjs](file:///c:/Users/мишка/Desktop/сайтик_бахчасарай/scripts/validate-project.mjs)).
3. `npm run test` — запуски unit-тестов Vitest.
4. `npm run test:e2e` — запуск E2E-тестов Playwright.

**Все 4 шага должны быть пройдены без ошибок (зеленые).**

### Правила написания тестов:
* Для каждого нового экрана или ключевой бизнес-фичи **обязательно** добавлять E2E-тест в [tests/e2e/smoke.spec.js](file:///c:/Users/мишка/Desktop/сайтик_бахчасарай/tests/e2e/smoke.spec.js).
* Селекторы в E2E: приоритет отдается `#id`, затем `[data-view]`, классы — в последнюю очередь.
* E2E-тесты выполняются в тестовой БД (`NODE_ENV=test`), которая сбрасывается при каждом старте сервера. Тесты авторизации должны генерировать уникальные данные (например, `ivan_${Date.now()}@example.com`).
