# Известные ошибки и найденные проблемы

Лог багов, найденных в ходе разработки. Отмечаем: статус, причина, как решено.

## Исправлено

### 1. Незакрытый div ломал вёрстку (index.html)
- **Симптом:** незакрытый `</div>` после `view-container` — разметка могла «разъезжаться».
- **Причина:** пропущен закрывающий тег.
- **Решение:** добавлен недостающий `</div>`.
- **Статус:** исправлено, проверено E2E-тестами и `npm run build`.

### 2. Prettier не мог разобрать HTML-шаблонные строки в js/app.js
- **Симптом:** `npm run format`/`format:check` падал с parse error.
- **Причина:** в скрипте есть закрывающие `</script>`-подобные последовательности в JS-шаблонных строках (в т.ч. внутри `renderSubjectNotes` и др.).
- **Решение:** настроен `prettier.ignore` для `js/app.js` + `index.html` (см. `.prettierignore`).
- **Статус:** исправлено.

### 3. Моноип/ранние JS-ошибки при загрузке
- **Симптом:** устаревшие `onclick`-атрибуты и порядок инициализации.
- **Причина:** монолитная инициализация на `DOMContentLoaded`.
- **Решение:** глобальная `init()` перерегистрирует все обработчики; все ссылки на элементы пересоздаются через `querySelectorAll`.
- **Статус:** исправлено; подтверждено E2E-тестами.

### 4. Дублирование элементов `#loginBtn`/`#logoutBtn` в сайдбаре
- **Симптом:** strict-mode-ошибка Playwright: `#loginBtn` resolved to 2 elements.
- **Причина:** `renderAuthHeader()` добавлял новый элемент в `#authHeaderArea` без очистки — при смене состояния (гость → авторизован) в DOM копились и кнопка «Войти», и бейдж пользователя.
- **Решение:** перед добавлением `authArea.innerHTML = ""` (срабатывает только при изменении сигнатуры пользователя, т.к. есть guard `lastAuthSignature`).
- **Статус:** исправлено.

### 5. После регистрации повторный вход отправлял `/register` (409)
- **Симптом:** E2E «авторизация: регистрация, вход, выход» — после регистрации и выхода повторный вход не срабатывал, модалка не закрывалась, тост «Пользователь с таким email уже существует».
- **Причина:** `authMode` оставался `"register"` после успешной регистрации — форма при повторном открытии снова шла на `/api/auth/register`.
- **Решение:** после успешной регистрации `authMode` сбрасывается в `"login"` и текст заголовка/кнопок модалки возвращается к режиму входа.
- **Статус:** исправлено.

### 6. E2E зависали в параллельном режиме
- **Симптом:** при `fullyParallel` и дефолтных воркерах (12) тесты падали по таймауту 30с в `beforeEach`/teardown («Fixture trace recording timeout»).
- **Причина:** 12 параллельных Chromium не влезали в 8 ГБ RAM (свободно ~2.7 ГБ) — браузеры зависали.
- **Решение:** `workers: 3` в `playwright.config.js` (в CI — 2).
- **Статус:** исправлено.

### 7. Back/forward: Chromium схлопывает соседние записи истории с одинаковым URL
- **Симптом:** E2E «навигация кнопками браузера» — `goBack` с `#notes` приземлялся не на subject-detail, а сразу на subjects (запись subject-detail пропускалась).
- **Причина:** sub-view пушился через `history.pushState(state, "", location.hash)` — URL `/#subjects` совпадал с URL предыдущей записи; Chromium объединяет/пропускает соседние same-document записи с одинаковым URL.
- **Решение:** sub-view получают уникальные hash-URL: `#subject-detail:<id>`, `#note-reader:<subjectId>:<noteId>`, `#quiz-player`, `#quiz-results`; `pushSubView(state, hash)` принимает URL явно.
- **Статус:** исправлено, проверено E2E-тестом.

### 8. E2E back/forward: тест ожидал нестандартную семантику истории
- **Симптом:** после `push → back → push(другая вью)` `goBack` шёл не в первую вью, а в начальную.
- **Причина:** это стандартное поведение браузера — новый `history.pushState()` обрезает forward-записи; тест был написан «от желаемого», а не от реальной семантики.
- **Решение:** тест переписан под стандартную семантику: `Forward` проверяется до нового pushState.
- **Статус:** исправлено (поправлен тест, а не приложение).

### 9. E2E авторизации не был идемпотентным (регистрация 409 при повторе)
- **Симптом:** второй прогон E2E «авторизация» падал — модалка не закрывалась после нажатия `#authSubmitManual`.
- **Причина:** фиксированный email `ivan@example.ru` оставался в `data/examhub.test.db` между прогонами; `POST /api/auth/register` возвращает 409 «Пользователь с таким email уже существует».
- **Решение:** email генерируется уникальным за прогон (`ivan${Date.now()}@example.ru`), имя для проверки выводится из email (`expectedName`).
- **Статус:** исправлено.
